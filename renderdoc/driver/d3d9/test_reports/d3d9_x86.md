# D3D9 in 32-bit programs

Step 2 of the plan: capturing 32-bit D3D9 programs, the way most D3D9 games are built, and replaying
them in the 64-bit UI. It works without changes to the D3D9 driver:

- `renderdoc.sln` builds for x86 with 0 warnings.
- The `[d3d9]` unit tests pass as 32-bit code.
- All 11 automated tests pass against 32-bit builds of the demos, captured by the 32-bit
  `renderdoc.dll` and replayed by the 64-bit one.
- A 32-bit demo launched, captured and opened from the 64-bit qrenderdoc shows correctly in the
  texture viewer, pipeline state and mesh viewer.

The only code change was to the demos project: upstream's Vulkan and D3D12 demos no longer compile
for 32-bit, so the 32-bit build leaves them out.

- **What I built:** this round's commit, on top of 576875216:
  - `renderdoc.sln` and `util\test\demos.sln`, Development, for both x64 and x86, with 0 errors and
    0 warnings;
  - the python module for Python 3.14, as before.
- **Machine:** Windows 11, RTX 4070 Ti.

## How a 32-bit program is captured

The 64-bit build can't inject into a 32-bit process itself. `win32_process.cpp` hands the launch to
the 32-bit `renderdoccmd.exe`, which injects the 32-bit `renderdoc.dll`. In a development build it
looks for that in `Win32\Development` next to `x64\Development`; an installed RenderDoc has it in
`x86\`. The 32-bit `renderdoc.dll` writes the capture. The 64-bit one replays it, the same as for a
64-bit program. The capture records the process's architecture, which the tests now check.

So both builds of `renderdoc.sln` are needed. There's nothing D3D9-specific in this: it's how
upstream captures 32-bit D3D11 programs.

## Builds

**`renderdoc.sln` x86** built with 0 warnings and 0 errors the first time. Before building I read
the D3D9 code for 32-bit problems; none showed up, and the build agrees:
- COM methods are declared `STDMETHODCALLTYPE` and the hook typedefs `WINAPI`, so calling
  conventions match on x86, where a mismatch crashes.
- Window handles are serialised as 64-bit values, so captures have the same format from both
  architectures.
- No code depends on `_WIN64` or SIMD.

**`demos.sln` x86** failed with 47 errors, all in upstream code the fork hasn't changed:

| Where | Why |
|---|---|
| `3rdparty/VulkanMemoryAllocator/vk_mem_alloc.h` | VMA casts between its handles and pointers. The demos' `vk_headers.h` makes 32-bit Vulkan handles a struct, and a struct doesn't cast to a pointer |
| `vk/vk_annotations.cpp` | passes a `VkImage`, a struct in 32-bit, where the annotation API takes a `void *` |
| `vk/vk_descriptor_buffer.cpp`, `vk_descriptor_buffer_analyse.cpp` | ambiguous overloads with the handle struct, and a `uint64_t` to `size_t` conversion |
| `d3d12/d3d12_primitiveid.cpp`, `d3d12_shader_debug_zoo.cpp` | `int` compared with `size_t`, a warning only where `size_t` is 32 bits, but warnings are errors |

Fixing them belongs upstream. `demos.vcxproj` now leaves `vk\` and `d3d12\` out of the Win32
build, with one conditional `ItemGroup`. Then the 32-bit demos built with 0 warnings and 0 errors
and list every D3D9 test. Nothing else in the demos includes those folders, and the x64 build is
unchanged: it was up to date after the change.

## Automated tests on the 32-bit demos

`python util\test\run_tests_local.py --x86 -t "^D3D9|D3D11_D3DPERF"`:

```
.. Demos running from E:\Projects\renderdoc\util\test\demos_x86.exe
## Tests complete summary: 11 passed out of 11 run from 202 total in 0:00:58.317352 ##
```

`--x86` is new in `run_tests_local.py`:
- It runs `util\test\demos_x86.exe`, with capture and replay still done by `x64\Development`.
- It stops with a message if `Win32\Development` hasn't been built.

`D3D9_Test` now checks every capture's recorded machine against the demos binary's PE header, so a
run can't quietly test the wrong architecture. Each of the 12 captures (the Reset test makes two)
logged:

```
** The capture was made by a 32-bit process (Windows x86 32-bit)
```

That covers, for a 32-bit program:
- hooking device creation;
- the overlay;
- every call serialised;
- initial contents, including depth stencils read back with the depth test, which compiles shaders
  in the captured process with the x86 `d3dcompiler_47.dll`;
- Reset during a capture;
- in-app captures;
- the 64-bit replay of all of it, with the checks the x64 run makes: formats, mesh output,
  overlays, pipeline state, resource contents and the structured export round trip.

The numbers:
- **Texture formats:** 31 passed, 0 failed.
- **Mesh output:** 18 passed, 0 failed.
- **Overlays:** 101 checks passed.
- **References:** each one the demo wrote under RenderDoc is identical to its native one, 293,903
  and 51,443 bytes.

The x64 run, after the same changes, still passes 11/11, and each capture reports
`Windows x86 64-bit`. Full output: `d3d9_x86/run_tests_x86_output.txt` and
`d3d9_x86/run_tests_x64_output.txt`.

### 32-bit and 64-bit native references

The two architectures' native references from the GPU, compared with each other:

- **`D3D9_Texture_Formats`:** identical.
- **`D3D9_Mesh_Output`:** 8 of 368 lines differ. In each one a colour channel is off by exactly
  1/255. They're in the `vs_1_1`, `vs_2_0 flow control` and `vs_2_0 DrawPrimitiveUP` draws:

```
L299 x64: row 0 0 COLOR.0=0.200000003,0.301960796,0.549019635,1 ...
L299 x86: row 0 0 COLOR.0=0.200000003,0.298039228,0.549019635,1 ...
L285 x64: ... COLOR.1=0.396078438,0.298039228,1 ...
L285 x86: ... COLOR.1=0.392156869,0.298039228,1 ...
```

That's not the GPU or RenderDoc. The demo gets these references from `ProcessVertices` on a
software vertex processing device, which runs on the CPU inside `d3d9.dll`. A 32-bit program loads
SysWOW64's `d3d9.dll` and a 64-bit one System32's, and the two round a shader's colour output to 8
bits differently. Both are within the mesh check's 1.5/255 colour tolerance, and each run was
checked against its own reference.

## In the UI

From the x64 `qrenderdoc.exe`, I drove the Launch Application dialog from a `--ui-python` script:
`demos_x86.exe D3D9_Mesh_Output`, working directory `util\test`. The rest I did by clicking:

1. The connection tab showed `demos_x86 [PID 69120]`, API "D3D9 (Active)". "Capture Frame(s)
   Immediately" captured frame 113393 (0.11 MB) with its thumbnail
   (`d3d9_x86/ui_1_capture_from_x64_ui.png`).
2. Double-clicking the thumbnail opened it: "loaded. No problems detected." The event browser has
   the 18 marked draws, from `FFP transform` to `vs_2_0 DrawPrimitiveUP`, and the Present.
3. At the `vs_1_1` draw (event 1507):
   - **Texture viewer:** the back buffer with the draw's output, and the usage markers on the
     timeline (`d3d9_x86/ui_2_texture_viewer.png`).
   - **Pipeline state:** the Vertex Shader page shows `Vertex Shader 90 (vs_1_1)` with its 256 float
     constants and the fixed function state (`d3d9_x86/ui_3_pipeline_vs.png`). The Input Assembler
     page shows the declaration (POSITION FLOAT3, COLOR D3DCOLOR as B8G8R8A8_UNORM, TEXCOORD
     FLOAT3), vertex buffer 87 with stride 28, and index buffer 88.
   - **Mesh viewer:** VS In and VS Out tables, and the preview with the selected triangle
     (`d3d9_x86/ui_4_mesh_viewer.png`).

The demo's log from that run had no errors.

## Not covered

- **A real 32-bit game:** the user tests that. The demos use little memory. A game that's close to
  its 2 GB (or 4 GB with large address aware) address space is the case to watch, since the shadow
  copies of default pool textures cost as much again (step 2b).
- **32-bit replay** (the x86 qrenderdoc): not tried. The x64 UI is the normal way to replay
  captures from 32-bit programs.
- **Global process hooking** (`renderdocshim32.dll`): not tried. The tests and the UI launch the
  program.
- **The Vulkan and D3D12 demos in 32-bit:** left out of the build, as above.
